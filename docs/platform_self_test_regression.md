# TestAuto 平台自举式全量回归

本文档记录“以 TestAuto 平台自身作为被测系统”的非 Agent 自动化回归基线。它不是演示数据，
而是可在前端维护、按业务域单独运行、也可由测试计划统一运行的正式测试资产。

覆盖分三层：

1. `COV-*` 接口契约层：每个非 Agent operation 都有保存用例，校验真实鉴权、参数验证、权限、
   资源不存在或受控错误状态；变更接口使用不存在的隔离 ID 或无效载荷，避免破坏业务数据。
2. `BIZ-*` 业务闭环层：按真实顺序创建、查询、更新、执行、复制/关联、下载并清理临时资源，
   验证跨步骤变量提取、模板传递、断言、前后置动作、异步执行、执行记录和报告。
3. `BIZ-E2E-*` 故障修复层：动态创建一条断言必然失败的 HTTP 用例，绑定带前后置动作的子场景，
   确认主步骤失败且后置脚本仍执行，随后创建缺陷、修复用例、升级场景快照、回归通过、生成报告、
   钻取明细、关闭缺陷并清理全部临时资源。
4. 总计划层：固定场景版本快照，以串行方式统一运行 34 个流程并聚合结果；单个业务域失败时继续
   收集其余结果，便于一次回归获得完整影响面。
5. 百级容量层：`【超大流程】TestAuto 非 Agent 全接口与业务闭环` 在一条场景内先执行故障修复
   闭环，再串行执行其余 106 个业务生命周期用例和 164 个接口契约用例，用于验证超过 100 个节点后的保存、编辑、
   运行、事件、变量传递、诊断和历史详情能力。

## 百级超大流程验收

场景 `108` 是独立可维护、可复制、可手动运行的正式流程，不是前端临时数据。它没有加入总回归
计划，避免日常总回归重复执行同一批 164 个契约用例和 106 个业务步骤；各业务域流程仍负责总计划内的精确定位，
超大流程专门负责容量和长链路验收。

2026-07-15 先以独立场景 `114` 产生运行 `331`，确认 64/64 步骤通过；随后通过正式异步执行接口
产生总流程运行 `335`，结果如下：

- 场景 v3 快照包含 304 个用例节点；加上 43 个随机值、固定值、条件、脚本和等待动作后，执行索引为
  `total_steps=347`、`passed_steps=347`，失败/超时/跳过均为 0。
- 运行状态为 `passed`，耗时 1,040,456 ms，最终事件序列为 1,043。
- 规范化诊断表保存 347 条步骤明细，运行详情接口可重新组装 347 条 `step_results`。
- 响应证据按需外置为 7 个压缩工件，原始总量 2,717,156 字节、落库总量 240,215 字节。
- 保存版本包含 34 个变量提取和 394 条来源到目标的模板绑定；路径中的嵌入式模板与保存用例
  `case_snapshot` 内的 header/query/body 模板均参与追踪。
- `BIZ-E2E-06` 断言子运行状态和主步骤为 `failed`、后置脚本为 `passed`；`BIZ-E2E-13` 断言
  修复后的前置、主步骤、后置均为 `passed`，随后计划报告、报告明细和缺陷 `closed` 终态全部通过。
- 完成后按项目扫描环境、用例、系统用例、缺陷、采集、场景、计划和流程等业务表，可见
  `AUTO-*` 临时资源为 0；软删除审计记录不计为可见残留。

`test_scenario_runs.step_results=[]` 是启用规范化步骤存储后的预期写入格式，不代表明细缺失；前端和
接口必须通过场景运行详情服务读取组装后的步骤结果，不能直接依赖数据库原始 JSON 字段。

## 正向业务闭环

- 项目、环境与敏感变量生命周期。
- HTTP 用例保存、更新、未保存执行、已保存异步执行和批量执行。
- 系统测试用例 CRUD、API 候选、关联保存、复制和批量删除。
- 缺陷富文本清洗、更新和状态流转。
- 浏览器采集、条目审阅、导入正式用例和回收。
- WebSocket 用例管理、未保存/已保存/批量执行及无服务端时的受控失败。
- 场景保存、脚本动作、执行、运行历史和详情。
- 测试计划保存、启停、执行、运行详情、报告结构、一次性 HTML 下载和删除。
- 可视化流程保存、校验、执行、报告和回收。
- 工作台、执行中心、执行记录与通知的真实事实投影。

## 已验证的平台缺陷

全量场景运行曾在读取大体积 `GET /scenario-runs` 响应时生成约 120 KiB 的压缩诊断证据，超过
MySQL `BLOB` 的 64 KiB 上限并导致业务请求 500。迁移 `0044_execution_artifact_mediumblob`
把 `execution_payload_artifacts.content` 在 MySQL 上扩容为 `MEDIUMBLOB`；脱敏、gzip、SHA-256、
项目隔离和单次分块读取上限均保持不变。修复后相关场景与总回归均通过。

304 节点运行还暴露了运行历史列表把大体积 `variables_snapshot/step_results` 与排序查询一起加载、
导致 MySQL `Out of sort memory` 和接口 500 的问题。列表查询现只投影运行身份、状态、进度和时间
字段，并返回空的详情占位；前端展开时再调用单条详情接口组装完整 347 步。修复后同一历史列表
返回 HTTP 200，详情仍保持完整证据。

## 外部依赖门禁

以下 operation 已进入契约层，但本地基线不把外部系统的成功响应伪装成平台通过：

- AI Provider 的真实生成/分析成功路径需要已配置 Provider，可能产生外部费用；本基线验证路由、
  鉴权、异步受理与错误边界，不声称验证模型质量。
- 媒体正向上传依赖可用 MinIO；无对象存储时只验证合同和受控错误。
- WebSocket 正向消息收发需要独立 echo 服务；当前业务闭环验证用例管理和连接失败诊断。
- Cron/Webhook 的真实时间触发分别依赖调度等待窗口和部署密钥；手动计划运行已完整验证。

这些门禁应在接入对应基础设施后增加独立的 integration profile，不能通过修改期望状态把外部故障
标记为成功。

## 重建与维护

生成器从运行中 OpenAPI 读取接口清单，不在源码中维护第二份路由表。默认只输出覆盖清单；
`--apply` 会删除本项目中带生成前缀的旧用例/流程/计划后重建，保留用户自建资产。

```powershell
$env:TESTAUTO_SELF_TEST_ACCOUNT = "<self-test-account>"
$env:TESTAUTO_SELF_TEST_PASSWORD = "<self-test-password>"
.\.venv\Scripts\python.exe scripts\bootstrap_platform_self_test.py `
  --project-id 10 --environment-id 13
.\.venv\Scripts\python.exe scripts\bootstrap_platform_self_test.py `
  --project-id 10 --environment-id 13 --apply
```

重建后在前端选择该项目和环境：

- “接口测试用例”应显示 310 条资产，并可按名称、方法、状态分页检索。
- “自动化测试流程”应显示 36 条流程；搜索“E2E”应能定位场景 `114`，搜索“超大流程”应能定位
  场景 `108`。场景 `108` v3 包含 304 个主用例节点和 43 个前后置动作，因此显示 347 个执行步骤；
  展开运行 `335` 后应显示 347/347 步骤通过，并能查看变量绑定、失败证据和修复证据。
- “测试计划”运行总回归计划；“执行历史”查看目标级汇总。

每次 OpenAPI 变化后先运行清单模式比较 operation 数，再重建并运行总计划。只有总计划通过、
无可见 `AUTO-*` 临时资源残留、数据库 migration 为最新 head 时，才能更新本文档的基线数字。
